This module answers: the system is built; how does the team use it well, and keep it healthy, without the architect in every issue? Three steps in order: configure the environment, lift the daily workflow, sustain operations.

5.1 Team setup D7 · Configure Claude tools and environments

  • Environment = shared configuration. For Claude Code: one project-level baseline — shared CLAUDE.md, agreed tools and MCP servers, agreed permission settings. Review, version, and improve once, instead of reconciling dozens of drifting personal configs.
  • Rollout = champion first, then waves. One champion per department migrates a real workflow first, absorbs early friction, builds local examples, tunes the shared CLAUDE.md, and becomes frontline support. Then roll out in small peer batches. Turning everyone on at once creates confusion and a retreat to old habits.
  • Set a cost policy before the first bill: default model, model allowlist, effort guidance, and per-person cost/rate caps. Ungoverned model choice multiplies across every member and every request.
Skill distribution methodBest fitsGovernance & rollback
Org-provisioned SkillEveryone in the org should have itOwner controls availability; can't pin a version, no native rollback (manual re-upload only). Weakest rollback
Plugin assigned to a user group or the whole orgA specific team, or anything needing controlled rolloutGroup targeting, install preference (required / default-install / optional / unavailable — added), version-controlled updates from a repo. Strongest people-facing governance
Claude Code project Skill (.claude/skills/)One team's coding convention across its own reposVersioned and rolled back via git; scoped only to the repo that contains it
API Skill (Messages API container)A partner's own product calling it programmaticallyGoverned in the calling system; explicitly pinned version; machine-to-machine

Practice: the Skill-distribution decision order

  1. Caller is a program, not a person? → API Skill. Decided before governance even enters.
  2. The artifact lives in a repo as a coding asset? → Project Skill. Rollback is inherited from git.
  3. Otherwise, for people teams: does it need centralized versioning and rollback, whatever the audience size? Yes → plugin. No, and it genuinely applies to everyone → org-provisioned Skill.

Audience size alone never decides step 3 — two questions about "everyone" can have opposite correct answers. Centrally managed Claude Code settings are a separate settings channel, not a Skill-distribution path — a common distractor.

Exam trap

Pushing a shared Skill as a flat package with no version and no rollback. One bad edit propagates to every team, producing bad output continuously during a manual fix. Any shared asset needs a version, an owner, and a rollback path.

5.2 Developer workflows D7 · Improve developer workflows

Put assistance inside the existing workflow (editor, code review, test loop), not in a side chat window. Encode conventions and repeated processes as Skills and project configuration.

StageClaude helps withReview discipline still required
Write codeBoilerplate, tests, a first implementation from a clear specCorrectness and safety review; the author understands what was generated
Review codeDiff summaries, flagged possible issues, explaining unfamiliar codeThe human decides; an AI flag is input, not a conclusion
DebugHypotheses from symptoms and tracesVerify with evidence before acting

Two adoption failures: uneven adoption (a few heavy users, many non-users — fixed with champion + wave rollout), and staying at simple chat (never progressing to tool use, codebase-aware help, Skills — having permission isn't real adoption).

Diligence = a verification checklist across four dimensions: correctness, security, maintainability, human understanding (the person merging can explain what the code does, including on untested inputs). Automate checklist items into tests and evals every change must pass.

Exam trap

Tests are green, review is approved, but the author can't explain how one input is handled. Pause the merge. The missing control isn't a linter or a faster model — it's the checklist's "understanding" and "security" dimensions.

5.3 Operational support D7 · Support debugging D4 · Diagnose

The architect's job is translating symptoms into architectural root causes, and teaching that path to the team so they handle it themselves next time. Fixing every incident personally is firefighting, not enablement.

SymptomLikely causeFirst action
Quality declining gradually, no code changeModel or prompt changed, or corpus growth caused retrieval driftRerun the eval set; check what changed in model, prompt, corpus
Latency spikingContext grew, a tool slowed down, or caching stopped hittingTrace the slowest link: tokens per request, slowest tool call, cache behavior
A tool fails intermittentlyAuthorization, rate limiting, or an unhandled error pathCheck that tool's auth and rate limits; trace one failed call end to end
Cost rising with flat usageModel tier silently escalated, or caching degradedCheck per-request tier and cache-hit rate against the budget model

Autonomy is built, not granted: a runbook (symptom → cause → action) and an escalation path (who owns what, when it leaves the team). Goal: the team only needs you for genuinely new problems.

Exam trap

Dashboards are green all quarter while answer quality declines, because corpus growth outpaced the index and the runbook has no entry for "quality declining, no code change." Raising the model tier, disabling the cache, or rolling back the last deploy are distractors. Check model, prompt, and retrieval drift first.

Your logged weak spot — Module 5

Configure Claude tools and environments: the relationship between CLAUDE.md and the system prompt. System prompt = Anthropic's, in the system field (the published regulation). CLAUDE.md = your repo's desk procedure, inserted into messages. Neither is enforced — both are guidance.

团队配置：共享基线（CLAUDE.md、工具与 MCP、权限）；先每部门一个 champion，再分批推广；上线前设好成本控制。

Skill 分发顺序：程序调用 → API Skill；代码库资产 → 项目 Skill；需要集中版本控制和回滚 → plugin；全员且不需版本 → 组织级 Skill。

开发流程：AI 嵌入现有流程；验证清单四维度：正确性、安全性、可维护性、提交者能解释代码。

运维：症状 → 原因 → 首个动作；质量缓慢下降先查模型、prompt、检索漂移。留下 runbook 和升级路径。
