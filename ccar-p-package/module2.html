This module answers: how do you move from a working prototype to a system that clears a security review and proves every change works? Five tools: an eval gate before you build, a cost/reliability model before you ship, a feasibility conclusion before you commit, an integration design that survives security review, and an experimentation method.

2.1 Eval as acceptance criteria D4

Write the eval suite before production code. It forces measurable success criteria, exposes assumptions while changes are cheap, and gates every later change.

  • Define the task: a measurable behavior, test prompts, a pass bar.
  • Build a golden dataset: representative inputs plus edge cases and counterexamples, with expected outputs.
  • Run automated code checks: pass/fail each.
  • Score behavior needing explanation with a judge model: score + rationale each.
  • Read by category, not just the average. A higher average that hides an edge-case regression is not an improvement.
Scoring methodUse forCostWeakness
Code-basedSchema, JSON parsing, regex, length, exact match, numeric comparison against source, whether an action fired, identifier leakage, required sections presentNear zero; never driftsCan't judge tone, reasoning, helpfulness
LLM-as-judgeQuality, instruction-following, reasoning, faithfulness, completeness, tone, safety handlingAbout one call per itemInconsistent at edge cases
Human reviewHigh-risk or novel behavior; calibrating the judgeHighest; sampling onlyLow throughput; reviewer-to-reviewer variance

Test: does this check need explanation? Wherever a deterministic check exists, use code — even for high-risk behavior ("no claim auto-denied" is a code check, not a judge call).

A rigorous judge: detailed rubric, a small fixed label set, a required rationale, calibrated against human labels, run on a different model than the one it grades. An uncalibrated judge is worse than none.

Volume beats perfection: many low-cost automated cases find more regressions and can run every change.

From requirement to criteria: write field names; set thresholds from business requirements, not whatever the prototype happened to score; turn failure modes into dataset categories; add noisy and adversarial input.

Multi-turn eval is its own category: the scoring unit is the whole conversation, judged against transcript-based golden sets.

Highest-risk moment: a stale eval. The prompt changes but the golden set doesn't — tests keep passing while measuring behavior that no longer exists.

Eval runs fail loudly; production degrades gracefully. A silent fallback-model switch during an eval run mixes two models' scores. For rate limits during batch eval: respect retry-after, limit concurrency, or use the Message Batches API.

2.2 POC to production D4 D3

A demo hides four things: cost at real scale, latency under concurrency, reliability when calls fail, and failure modes on unexpected input. Also get an early read on business metrics as soon as possible.

  • Build cost and latency models before finalizing the architecture: call volume × tokens per request (input and output) × model tier.
  • Model the token distribution, not the average. A long tail can skew average-based estimates 2–3×.
  • Design to p95, not the median. Example: 90 requests at 2s + 10 at 30s → average 4.8s (meets a 5s SLA) but p95 is 30s (fails it).
  • Prompt caching is the strongest lever for long, stable prefixes. Risk: any part of a cached prefix that should reflect live state goes stale.

2.3 Sizing, feasibility, ROI D1

Three sequential questions, each feeding the next, all landing in the SOW: can we afford to run it? can we build it? is it worth it?

Sizing

  • Get call volume from the business owner, not sampled from logs. Count follow-up calls in multi-turn conversations.
  • Tokens per request computed as a distribution.
  • Monthly cost = input tokens × input price + output tokens × output price, cached tokens at cache-read price, plus cache-write cost. Compare against the budget cap. If the SLA allows async, price the Batch API discount (confirm BAA coverage for regulated data).
  • Sensitivity analysis: double the call volume; shift tokens toward the long tail.
  • Over budget → change the architecture before writing code (narrow scope, cheaper tier, caching, batching).

Feasibility

  • Scoping: business goal → capability list → owner per capability → boundary conditions → SOW scope clauses.
  • Check every capability against the four model properties. Working memory is the one most often overlooked: a single long document may fit; the whole corpus never will — exactly why RAG exists.
ConclusionYou must deliver
Feasible as scopedWritten assumptions (the conclusion changes if an assumption changes)
Feasible with constraintsEach constraint and its failure mode if violated — the constraint is itself architecture
Not feasibleThe binding constraint, and what scope reduction would flip the conclusion

Practice: name the one load-bearing constraint

  • Research assistant, 50 reports/week, 24h delivery, $500/mo → feasible as scoped; no binding constraint. Adding full human review everywhere is not the binding constraint.
  • Carrier-email extractor, 5,000/day, writes to the order system → feasible with constraints: extraction accuracy before a transactional write → code-based eval + a human gate on low-confidence writes.
  • Trading advice within 2 seconds → conclusion pending: verify the live-quote tool + model round trip can fit in 2s first. A human gate doesn't fit inside 2 seconds.

Rule of thumb: write-side errors with consequences → accuracy eval + HITL. Real-time data → a tool + a latency budget. An unknown that decides the conclusion → a technical spike first.

ROI by five value pillars

Pillars: efficiency, transformation, productivity, solution cost, performance SLAs.

  • Baseline in business units, measured from the owner's real data.
  • Expected state in the same unit, keeping residual HITL labor.
  • Subtract run cost from the sizing model (distribution, not average).
  • Payback period, including build cost, with a sensitivity check.

Three classic mistakes: an estimated baseline instead of a measured one; HITL designed in but modeled as fully automated; run cost computed off the average.

Scope vs. sizing vs. feasibility vs. reliability: scope = what (qualitative); sizing = run cost; feasibility = can the design meet the bar; reliability = can it survive infrastructure failure in production. Compensating controls for model limitations (schema, retrieval, HITL) are not reliability controls (retry, breaker, fallback).

Order: compliance filters routes and entry points first, then identity, authorization, data handling, observability.

Log four things per request: request (model version, input tokens, prompt ID); response (output tokens, latency, stop reason); context (user role, session ID, cache hit); outcome (did downstream accept it? rejection signal?).

Tool least privilege: review each tool as required vs. merely convenient; remove out-of-scope tools and record why; scope each subagent's tools. Removal beats logging or confirmation (Sample Q1).

Capability-bloat test: does each tool serve a task users actually do? Removal closes read risk, write risk, and future misuse at once. Check whether your reasoning matches the specific risk the stem names (read of unauthenticated data vs. write).

Multi-tenant: one API key per tenant for rate-limit attribution and isolation.

Data retention added: Anthropic doesn't retain API content by default, but your own application logs record every field you sent. Redact before the call; redacting logs after the fact is the most expensive fix.

Entry points from an integration lens: Claude Code can never be a multi-tenant product's backend; Agent SDK doesn't fit single request/response; MCP adds a protocol hop that makes tool debugging harder.

2.5 A/B testing, shadow testing, observability D4

Experiment requirements — all set before the run

  • A falsifiable hypothesis: treatment, one primary metric, minimum effect, guardrail metrics.
  • Randomized, consistent per user or session.
  • Sample size depends on baseline, minimum detectable effect, power, significance. LLM variance means larger samples (course example: detecting 70%→75% at 80% power / 5% significance needs ≈1,500 per arm).
  • Choosing a metric after seeing the data is outcome-shopping.

Practice: the experiment design plane — a logged weak spot

Keep two axes separate. Effect size = how large the measured-metric difference is. Confidence = the cost of being wrong (consequence, reversibility) — driven by risk, independent of effect size.

  • Sample size rises with confidence, falls with effect size; halving the effect roughly quadruples the sample.
  • Medical intake summarizer, minor change → small effect / high confidence (largest, slowest sample).
  • Switching a formatting task from Sonnet to Haiku, cost change big and reversible → large effect / moderate confidence; watch quality guardrails.
  • Adding a routing category that takes 30% of traffic → large / high (blast radius). FAQ wording tweak → small / low.

Reading results: statistically significant ≠ practically significant. Confirm the gain is worth the maintenance and that no guardrail metric (cost, p95) got worse. Even an overall improvement with a high-risk segment regression is a guardrail failure (overall 91%→93% while a key segment drops 85%→70% = don't ship). Register segment-level guardrails before the run.

Trap: a few dozen sessions per arm, a few points' improvement, uncontrolled input mix, metric chosen after the fact. That's noise.

Shadow testing: mirror live traffic to the new version, serve users only the current version, score the shadow output offline. Fits when a single bad output is unacceptable (regulated) or traffic is too low. You lose real user signal and depend on a rubric or gold answers.

Observability layers D3 D4

  • Request tracing: model and version, tokens, latency, stop reason, tool calls.
  • Aggregate metrics: cost per request, p50/p95, task success from downstream acceptance, error rate by type. Break down per request; an average hides a few costly or wrong requests.
  • Anomaly alerts: e.g. cost over 150% of a 7-day average, p95 above the SLA. Output drift needs periodic distribution comparisons.
  • Change attribution: model drift (same input, different behavior), data drift (input changed), model-update effect (version changed). Each has a different fix.

LLM failure is quiet, not a crash. Error rate, latency, and uptime can all stay green while quality erodes. Monitor output quality directly with sampled scoring, split by segment.

中文要点

Eval 先于生产代码。确定性检查即使高风险也用代码；需要解释的用 LLM-as-judge，并用人工标注校准。

成本按 token 分布估算，延迟按 p95 设计。重试贴近 API 调用，circuit breaker 放服务边界，fallback 放编排层。

可行性三种结论，要找出唯一的关键约束。ROI 用五个价值支柱，基线必须实测。

集成五层：合规、身份、授权、数据/PII、可观测性。身份在服务端校验；工具最小权限，删除优于记录或确认。

A/B 测试前先定主指标和样本量；高风险细分退步就不能上线。LLM 出错往往悄悄发生，要按细分监控输出质量。
